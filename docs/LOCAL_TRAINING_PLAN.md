# Локальные эксперименты и отложенное предложение stair-v4

**Последующее решение пользователя,23 сентября 2026:** число и смысл входов сохраняются как у референса,57→16. Расширение ABI не одобрено. Stair-v4 не реализована и сейчас не является следующим разрешённым запуском. Текущая работа — автономный серверный inverse57; локально выполняются оценка и доставка. [Статус обеих линий](TRAINING_STATUS.md).

Ниже сохранено прежнее исследовательское предложение. Все последующие формулировки «следующий», бюджеты v4 и новый ABI относятся к **отложенному предложению**, а не выполняемой работе.

## Решение и исходная точка

Следующая линия — отдельная goal-conditioned `stair-v4`: сначала диагностический teacher, затем student с доступными наблюдениями. Короткие 57-D stair fine-tune закрыты. `rough57` сохраняется как исследовательский контроль; он не прошёл финальный rough gate и не является проверенной безопасной fallback-политикой.

| Что подтверждено | Что это меняет |
|---|---|
| Control57, seeds 54/55: 1106/1536 циклов, 169 unsafe, 215 stop failures | Остановка — только часть проблемы; одновременно нужны traversal и safety |
| Base-velocity actor: 1064/1536, 174 unsafe; moving teacher anchor: 1092/1536, 170 unsafe | Добавление скорости или сохранение старых действий само по себе не решило задачу |
| Slow-brake + ramp10: stop failures 82→43, но safety gate провален | Внешнее торможение не является основанием продолжать прежний PPO |
| Rough seed 55: 1521/1536, inverse 293/306, провал одного mesh gate | Rough stage остаётся открытым независимо от успехов stair specialist |
| 4096×25×24 = 2 457 600 переходов за 74.35 с в прежнем pilot | 4096 — кандидат для нового runtime; скорость и peak памяти v4 ещё надо измерить |

Источники: [control57/basevel](results/2026-09-23-actor-base-velocity.md), [anchor](results/2026-09-23-moving-teacher-anchor.md), [brake screen](results/2026-09-23-slow-brake-wheel-screen.md), [rough final](results/2026-09-23-rough-final-selection.md), [масштабирование](results/2026-09-22-4096-env-scaling.md). Суммы control57 сверены с 12 файлами `logs/stair_benchmark/basevel_control57_s{54,55}_v3open128_*.json`; агрегат не заменяет отдельные строки и training seeds.

В текущем коде actor получает velocity command, а passage/hold/restart зависят от положения и таймера вне actor. Недостаточная наблюдаемость — рабочая гипотеза, а не доказанная причина всех отказов. V4 сначала проверяет полезность новой постановки; один успешный teacher не доказывает sim2real или причинный эффект каждого нового входа.

## 1. Контракт до первого PPO run

Реализовать отдельные Isaac Lab MDP environment/agent configs, command term и evaluator вне `vendor/`. Существующий `train_stair_b2w.py` поддерживает 57/60-D velocity task; его флаги не реализуют v4. Использовать RSL-RL и текущий pinned runtime, не совмещая смену задачи со сменой алгоритма/версий.

| Часть | Зафиксировать в manifest |
|---|---|
| Действия | 12 joint-position targets ног + 4 joint-velocity targets колёс; прежние порядок, signs, scales, limits, 50 Hz |
| Общие входы | Проприоцепция, previous action, команда; relative target `Rz(-yaw)·(p_goal−p_base)`, нормировка и clipping |
| Режим и фаза | Отдельно terrain mode `flat/up/down` и phase `approach/hold/restart`; остаток hold-time, если переход зависит от таймера. Не объединять hold и restart в один код |
| Teacher actor | Те же входы + точная симуляционная `base_lin_vel`; точная relative target разрешена только как диагностическое допущение. В первом опыте terrain scan остаётся у critic |
| Critic | Actor inputs + terrain heights, true velocity, contacts, применённые friction/payload и состояние задания |
| Student | История проприоцепции/действий, текущие target/mode/phase; источник target и pose/velocity estimate, частота, задержка и reset history описаны отдельно |

Размеры тензоров, порядок каждого блока и источник каждого входа записать в версионируемый ABI до обучения. History не заменяет локализацию и источник цели: при отсутствии проверенного источника relative target результат остаётся симуляционным. Ground-truth target/velocity у teacher не должны незаметно сохраняться у student.

Инициализация teacher — actor локального rough seed 55 `model_349.pt`, SHA-256 `765fe2a4cd1438ca3e81c387be570473c5dd3f9db656c4f064ec7a903dd802ed`, только как warm start. Старые 57 слотов сохранять для переноса, новые входные столбцы обнулить; проверить action parity ≤1e-5 до первого update. Critic/optimizer создать заново, счётчик v4 начать с нуля. Полный resume разрешён лишь между совместимыми v4 checkpoints; сохранять RNG, curriculum, normalization и phase/history state либо явно документировать reset сред при возобновлении.

Reward: potential progress внутри неизменной цели/фазы, безопасный reach/hold и отдельный полный цикл. Смена цели не должна создавать бесплатный progress bonus. На каждой фазе учитывать base/hip contact, tilt, joint/actuator limits; приоритет unsafe выше success. Зафиксировать terminal/truncation semantics и одинаковую логику в train/eval. Веса torque/action-rate начать с текущего baseline; логировать saturation, RMS torque и power proxy отдельно для ног/колёс. Эти proxy не подтверждают отсутствие перегрева без тепловой модели приводов.

Обязательные проверки: target frame при yaw 0/±90°/180°, знаки up/down, порядок 16 действий, wheel-position masking, границы фаз/таймера, reset только завершённых сред, terminal observation до autoreset, несовместимый ABI, save/load. Smoke 64–256 сред проверяет конечные наблюдения/loss, физически допустимые reset и один PPO update. Mid-flight/landing resets добавлять только после probes контактов и высоты, не телепортировать робота внутрь ступени.

## 2. Последовательность экспериментов

Численные пороги ниже — проектные решения для следующих опытов, не уже достигнутые результаты. Все success-gates считаются отдельно по направлению и строке; среднее между up/down не закрывает провал одного направления.

| Шаг | Работа и бюджет | Условие перехода |
|---|---|---|
| P0. Контракт и smoke | ABI, единый cycle evaluator, frozen eval manifest; 64–256 сред, затем ресурсный probe 2048/4096 | Проверки выше прошли, нет NaN/OOM; сохранение/возобновление воспроизводимы в заявленных пределах |
| P1. Flat goal teacher | Один seed 54; reach → brake → hold → новая/reverse цель; первый блок до 100 updates | ≥95% полных циклов в каждой flat строке по 128 эпизодов; unsafe не хуже контроля при тех же стартах |
| P2. Fixed stair teacher | Продолжить тот же seed, 14/32 см, 6 ступеней, up/down, ограниченная randomization; до 300 updates суммарно P1+P2 | ≥85% (≥109/128) в каждой development строке на двух последовательных проверках; unsafe не выше замороженного контроля в той же строке |
| P3. Геометрия и устойчивость teacher | Только после P2; ступенчато расширить rise 5–20 см/run 25–42 см, длину марша/площадок, heading/start velocity; максимум 1000 суммарных updates первого teacher | ≥95% (≥122/128) на каждой development строке целевого диапазона и однократная validation выбранного teacher; safety gate сохранён |
| P4. Student | Один пилот: history encoder, distillation на собственных rollout states, затем PPO; бюджет отдельно фиксируется до запуска | Нет oracle-входов; ≥95% по строкам, flat/rough gates для заявленной области, export parity history/estimator |
| P5. Воспроизводимость | Замороженный полный рецепт teacher→student повторить на seeds 55/56; seed 54 учитывается только при том же рецепте и бюджете | Все 3 seeds проходят gates; публикуются разброс и worst-row, не выбирается один удачный seed |
| P6. Финальный кандидат | Freeze weights/ABI, закрытая stair suite один раз, export parity и MuJoCo sim2sim | Release-критерии [общего плана](PROJECT_PLAN.md); SDK2 replay/dry-run — следующий отдельный этап |

В P1 контроль — тот же actor с заранее фиксированным goal-to-velocity adapter; в P2/P3 — control57 seed 55 `model_398.pt`, SHA-256 `f5d7403f98853374b3cdaf6dc329461b29f0f0658e308c0d6a47b890c2371ff2`, с теми же геометриями, стартами, horizon и правилами оценки. Adapter, checkpoint и profile входят в manifest; baseline измерить до PPO. Это диагностический reference, не причинная A/B-абляция. Результаты старой v3 suite сравнивать напрямую только при совпадении протокола; смена постановки/критерия означает новую таблицу baseline.

85% — разрешение расширять опыт, не допуск к релизу и не основание сразу копировать слабого teacher в student. До P3 высокий результат на 14/32 не переносится на весь диапазон. DR расширять после nominal gate по измеримым friction/mass/COM/actuator/noise/delay параметрам, по одному семейству. Не сочетать широкую DR, новую геометрию и смену rewards в одном опыте.

Если одна up/down ветвь не улучшается при прогрессе другой, сначала проверить отказы по фазам и coverage. При сохранении конфликта на двух контрольных интервалах — отдельные up/down experts с новым зафиксированным бюджетом. Объединение разрешено после их отдельных gates. Rough57 допустим как исследовательский replay teacher, но не как доказательство прохождения rough acceptance; автоматическое переключение политик также требует отдельного transition test.

## 3. Бюджет, evaluation и остановка

Основной режим — один последовательный headless процесс на RTX 4080 Laptop, без GUI/камер и конкурирующих собственных train/eval. Стартовый кандидат — 4096 сред × 24 шага rollout, как в текущем B2W PPO config. V4 memory/throughput измерить заново; 2048 — запасной вариант при недостаточном запасе VRAM/RAM или деградации длительной производительности. Настольная RTX 4070 Ti подключается после отдельной квалификации, сервер в эту линию не входит.

| Бюджет при 4096×24 | Переходы среды | Назначение |
|---|---:|---|
| 25 updates | 2 457 600 | Интервал development screen |
| 100 updates | 9 830 400 | Первый flat блок / контроль расширенного набора |
| 300 updates | 29 491 200 | Начальный лимит всего teacher feasibility |
| 1000 updates | 98 304 000 | Максимум первого teacher с условными продлениями |

При 2048 средах равный sample budget требует вдвое больше updates; это другой PPO batch, а не эквивалентный алгоритмический опыт. Фиксировать `env_count × rollout × updates`, PPO epochs/minibatches, KL, entropy и value loss. Пределы 300/1000 — инженерный бюджет warm start, не гарантия сходимости. Номер файла parent не является числом новых updates.

Каждые 25 updates сохранять checkpoint и выполнять небольшой постоянный development screen: 14/32 up/down и flat stop/restart; на строку 128 эпизодов. Каждые 100 updates и на границе P2/P3 — полный development набор текущей стадии. Evaluation не обновляет веса/normalization/curriculum. Время startup, training, evaluation, peak VRAM/RAM, sustained throughput и GPU-hours до gate учитываются раздельно; старые 74.35 с не экстраполировать в обещание времени обучения v4.

Правило продолжения: безопасность — обязательный фильтр; среди допустимых checkpoints выбирать по worst-row full-cycle, затем сумме циклов, unsafe, passage/hold. После не менее 100 updates на неизменной стадии — остановка при пяти подряд screens без улучшения worst-row хотя бы на 2/128 относительно лучшего допустимого результата. Новый curriculum stage начинает новый счётчик plateau, но не обнуляет общий бюджет. Рост unsafe в двух screens подряд требует остановки и разбора, а NaN/OOM/нарушение контракта — немедленной остановки.

До 300 updates можно продолжать при прогрессе flat/фаз, даже если 85% ещё не достигнуты. Сверх 300 — блоками по 100, только если последние пять screens улучшили worst-row минимум на 2/128 без ухудшения safety. При отсутствии прогресса составить failure report и изменить одну подтверждённую причину; не продлевать только из-за роста train reward. Student/трёхseedовый бюджет не расходуется до соответствующего teacher gate.

## 4. Защита оценки от подбора

До первого PPO сохранить отдельный v4 eval manifest и SHA-256: геометрия, направление, начальные состояния, seeds, команды/цели, horizon, правила success/unsafe/stop/restart, число эпизодов. Добавить поддержку v4 отдельным evaluator: нынешний `eval_stair_suite.py` понимает v2/v3 и по умолчанию выбирает v2.

- **Development:** открытые stair 3001/3002/3003 и новые заранее фиксированные обучающие диагностические случаи; rough 2005/2006/2009/2010, ранее использованные 2011–2013 теперь также считаются открытыми. Только этот набор используется для curriculum, early stop и выбора checkpoint.
- **Validation:** новые геометрии/старты и seeds, отсутствующие в предыдущих отчётах и rollout training. Конкретный список фиксируется на P0. Его запускать для выбранного teacher и затем student на границах этапов, не каждые 25 updates. Если по отказам validation меняется рецепт, этот набор становится development, для нового подтверждения выделяется следующий.
- **Final test:** stair 4101–4104 из прежнего manifest остаются неиспользованными до одного выбранного финального кандидата; на v4 сохранить физические случаи, зафиксировать новый task adapter. После просмотра нельзя называть этот набор закрытым для повторного подбора. Новый финальный rough набор нужен отдельно: 2011–2013 уже использованы.

V3 задаёт 128 эпизодов на строку, horizon 900 policy steps, hold 100 шагов, speed ≤0.15 м/с, drift ≤0.35 м и restart ≥0.35 м. Сохранить отдельный совместимый v3 отчёт для сравнения. Для v4 заранее определить допуск попадания в target и непрерывное удержание; нельзя выдавать v3 проверку скорости только на границе hold за устойчивость на всём интервале. Не ослаблять критерий после просмотра результатов.

Полный цикл оценивается только из approach starts. Mid-flight/landing/restart resets полезны для обучения и отдельной фазовой диагностики, но не пополняют знаменатель full-cycle success. Все исходы должны быть взаимоисключающими и давать сумму N: success, unsafe, stop failure, timeout, incomplete. Публиковать причины контактов/наклона/limits, stop drift/speed, saturation/torque/power proxy, Wilson intervals по строкам и разброс training seeds; 128 копий одной геометрии не равны 128 разным лестницам.

Rough/flat regression обязательна для единой student policy, заявленной как замена rough57. Диагностический stair teacher оценивается в своей области и не обязан сначала становиться универсальной rough-политикой; это не закрывает этап rough. Для полного релиза остаются ≥95% по каждому rough family на каждом mesh (при N=102 минимум 97 успехов), flat success/tracking и допуски regression из общего плана. Пороги 85/95% здесь относятся к наблюдаемой доле успехов; Wilson interval публикуется отдельно и не выдаётся за уже доказанную нижнюю границу 95% надёжности.

## 5. Ближайший результат работы

Первый следующий результат — реализация и проверка v4 контракта/evaluator, baseline на фиксированном наборе и ресурсный smoke. Затем — один teacher feasibility run с одним config и явным решением по каждому gate. До этого новые массовые запуски не нужны.

Не возвращать без новых данных brake/min-speed sweeps, wheel clamps, stop pulses, reward-weight-only и 25–50-update velocity-only fine-tune. Причинную абляцию target/phase можно поставить после успешного v4 teacher при одинаковых инициализации, задаче, optimizer и sample budget; это отдельный опыт, не повтор прежнего micro-tuning.

Методическая опора: position-based task и явный stair mode у [Chamorro et al.](https://arxiv.org/abs/2402.06143); разделение base policy/adaptation у [RMA](https://arxiv.org/abs/2107.04034); experts → DAgger → RL fine-tuning у [Parkour in the Wild](https://arxiv.org/abs/2505.11164). Это основания проверяемых гипотез, а не подтверждение результата на B2W; последняя работа использует depth и не доказывает достаточность blind student.
